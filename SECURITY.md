# Безопасность PinPage

## Что уже сделано

- **Пароли хешируются PBKDF2-SHA256 с солью** (100 000 итераций) вместо
  слабого несолёного SHA-256. Формат: `pbkdf2$<итераций>$<соль_b64>$<хеш_b64>`.
  Старые пароли (sha256-хекс или открытый текст) принимаются при входе и тихо
  мигрируют в PBKDF2.

## Что осталось (требует доступа к Supabase-дашборду)

Сейчас приложение ходит в базу **только по публичному `anon`-ключу** и не
использует Supabase Auth. Следствие: любой, у кого есть этот ключ (а он лежит
в открытом клиентском коде), может читать и менять данные других пользователей.

Правильное решение — перевести вход на **Supabase Auth** и включить
**Row Level Security**. Полная миграция описана в
[`sql/security.sql`](sql/security.sql). Кратко это три шага:

1. **Supabase Auth.** В дашборде включи Auth (email/password). Клиент переходит
   с `DB.getUser/setUser` на `supabase.auth.signUp/signInWithPassword`; профиль
   хранится в `public.users`, связанном с `auth.users.id`.
2. **Перенос существующих аккаунтов.** Для каждого username создаётся
   auth-пользователь (скрипт с service_role-ключом), в `public.users`
   проставляется `id = auth.uid()`.
3. **RLS.** Выполнить политики из `sql/security.sql` и удалить колонку
   `public.users.password` (пароль начинает хранить Supabase Auth, bcrypt).

> Пока миграция не выполнена, публичный anon-ключ остаётся уязвимостью —
> PBKDF2 усложняет кражу паролей, но не закрывает доступ к данным.
